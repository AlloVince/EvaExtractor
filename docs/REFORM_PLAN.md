# EvaExtractor 整改清单

这份清单只列出**不破坏现有接口**的整改方向，按「低风险 / 中风险 / 高收益」分级。
目标是让项目更符合当前社区的 TypeScript / Node.js / CI / lint / 测试实践，同时尽量保持用户侧用法不变。

## 低风险

这些项通常只涉及内部实现、文档或构建配置，优先级最高。

### 1. 收紧内部类型

- 把 `any` 逐步替换为更具体的类型
- 把 `Record<string, any>` 收敛为更清晰的结构
- 给公开方法补齐返回类型
- 给内部帮助函数补齐输入约束

收益：

- 减少 lint 噪音
- 提升可读性和重构安全性
- 让 TypeScript 更早暴露问题

### 2. 清理历史拼写和命名

- `transferedItem` 这类历史拼写保留兼容，但内部新增代码统一使用正确拼写
- 新增辅助方法时使用更一致的命名风格

收益：

- 降低后续维护认知成本
- 让新代码更统一

### 3. 统一 Node 原生 API

- 继续用 `node:` 前缀导入内置模块
- 继续优先使用 `fs/promises`、`stream/consumers`、`crypto` 等原生能力
- 避免再引入“只做一层薄封装”的依赖

收益：

- 依赖更少
- Node 24 兼容性更稳
- 安装和发布更轻

### 4. 补齐小而稳的测试

- 给 `DatabaseIterator` 补分页行为测试
- 给 `OssIterator` / `MinioIterator` 补最小 mock 测试
- 给 `humanFileSizeToBytes()` 补非法输入测试

收益：

- 更容易防止回归
- 改内部实现时更安心

## 中风险

这些项会影响配置或内部架构，但仍可保持外部接口不变。

### 1. 现代化 `package.json`

- 补 `exports`
- 补 `types`
- 补 `files`
- 明确只发布需要的产物

收益：

- 发布面更现代
- 让消费者的导入方式更明确
- 避免意外暴露仓库内部文件

风险：

- 需要确认旧入口是否仍被外部依赖

### 2. 统一构建输出

- 让源码、测试、构建产物的目录关系更明确
- 避免根目录保留旧的生成 JS 文件
- 让构建结果只出现在 `lib/`

收益：

- 结构更清爽
- 更适合 CI 和发布

风险：

- 需要确认外部是否直接引用根目录遗留 JS

### 3. 让 lint 与 TS 配置一致

- ESLint 继续用 `typescript-eslint`
- TypeScript 固定稳定版
- `tsconfig` 和 ESLint 的文件范围保持一致

收益：

- 少一些“lint 过了、类型没过”或反过来的不一致

风险：

- 依赖版本需要同步管理

### 4. 收敛测试运行方式

- 让 `npm test` 只依赖一种固定方式
- 避免编译和测试入口出现多套逻辑

收益：

- CI 更稳定
- 本地复现更简单

风险：

- 需要确认本地和 CI 的一致性

## 高收益

这些项会明显改善项目现代性，但更值得分阶段推进。

### 1. 迁移到更标准的发布入口

- 采用 `exports` + `types`
- 保持 CommonJS 消费兼容，必要时再规划 ESM 迁移

收益：

- 发布体验更现代
- 更符合当前 npm 包最佳实践

### 2. 把配置文件分层

- 将 CI、lint、测试、构建配置分开管理
- 用专门文件承载专门职责

收益：

- 维护边界更清楚
- 方便未来拆分工作流

### 3. 把可选外部集成显式化

- 把 Ali OSS / MinIO 依赖路径写得更清楚
- 让 peer dependency 的使用说明更完整

收益：

- 更少安装困惑
- 更少运行时误用

### 4. 逐步减少“宽松入口”

- 尽量减少 `any` 和不透明对象
- 把外部 SDK 边界封装得更小

收益：

- 更容易在未来做大版本升级
- 更容易做自动化重构

## 推荐执行顺序

1. 补测试
2. 收紧内部类型
3. 统一 lint / TS 配置
4. 现代化发布入口
5. 再考虑更大的结构调整

## 本阶段建议不碰的地方

- 不改对外方法名
- 不改现有 processor / fetcher / storage / iterator 的语义
- 不引入额外依赖，只为解决可以用原生能力解决的问题
- 不在没有测试覆盖的情况下做大规模重构
